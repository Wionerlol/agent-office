Agent Office
日常使用指南

先看办公室，找到重要 Agent，选中它，沿明确关系检查上下文，再回到全局视图。接下来先在真实工作中使用并记录问题，再决定下一步开发。

master · PR #12 已合并角色 / 空间 / 协作 / 焦点本地工具

本指南对应合并提交 ec62c60 的应用功能，覆盖 Phase 1–4C。它可直接在浏览器中打开，或在服务运行时访问 http://127.0.0.1:8000/guide。页面样式与示意截图均内嵌，支持离线阅读和打印。

建议路线：启动服务 → 用模拟模式熟悉操作 → 接入一个真实 Agent → 有明确线程 UUID 时启用原生观察 → 连续使用并记录实际问题。没有 UUID 也可以使用基础观察模式。

1 · 启动与更新

需要 Git、uv、Python 3.13+ 和 Node.js 22。下列命令在 Agent Office 仓库根目录执行。已有本地配置请保留，不要用示例文件直接覆盖。

git switch master
git pull --ff-only
uv sync --frozen
cd frontend
npm ci
npm run build
cd ..
uv run agent-office

打开 http://127.0.0.1:8000。正常使用保持这个服务终端运行；第二个终端用于启动 Agent。默认地址是 127.0.0.1:8000，若你的本地 YAML 修改了端口，请同步修改网页和 wrapper 地址。

这次 master 同步已完成。前端升级后务必重新 build，服务读取的是 frontend/dist；如服务已运行，更新代码/配置后重启 Agent Office 服务即可，不要因此重启共享 Codex daemon。关闭 Agent Office 通常在其终端按 Ctrl+C。

在另一个项目里使用命令

uv run 默认使用当前项目。若已经切到工作仓库，用 --project 指向 Agent Office；占位路径请替换成真实路径。

uv run --project /path/to/agent-office office-run codex   --id lead --name Lead --role lead --repo /path/to/your-repo

所有例子中的 KNOWN_UUID、EXACT_UUID 和 /path/to/... 都是占位符。不要原样当成真实 ID 或目录执行。

2 · 先体验模拟团队

访问 http://127.0.0.1:8000/?demo=true。初始有 9 个角色，包括 Backend、Tester、Researcher、Reviewer、Lead，以及等待用户输入的 Frontend Engineer。

  1. 选择 Tester：观察名字底板和脚下强调，以及 Lead 正在等待 Tester 的协调线。
  2. 在详情中点击 Parent Agent → Lead，再点击 Children 或 Waiting on 中的 Tester，练习关系导航。
  3. 选择其他人时确认 NEEDS YOU / ? 仍明显；按 Escape 回到全局视图。
  4. 保持模拟运行约半分钟：会看到 Test Partner 出现、Lead 等待、子 Agent DONE、离场，以及 Reviewer 的 ERROR/恢复。
  5. 用 Pause simulation 暂停后续脚本变化；短暂交互 cue 仍按原期限消失。Resume 恢复脚本。
  6. 用 Tab、Enter/Space、Escape 操作 Team 按钮；缩窄窗口，检查下方详情；在操作系统开启减少动画后再观察。

模拟使用和真实 Agent 相同的前端模型与显示路径，但模拟现象不是原生能力证据。退出模拟请打开不含 ?demo=true 的首页并重新加载。模拟模式不会控制真实 Agent。

3 · 接入真实 Agent

先运行 Agent Office 服务，再在第二个终端使用 wrapper。为了避免多进程同名冲突，每个独立实例使用不同的 --id。

# 在 Agent Office 根目录执行；项目路径替换为你的工作仓库
uv run office-run codex --id lead --name Lead --role lead   --repo /path/to/your-repo --task "Implement the feature"

# 另一个终端；这是显式声明关系的独立进程，不代表原生自动 spawn
uv run office-run codex --id tester-1 --name Tester --role tester   --parent lead --repo /path/to/your-repo --task "Verify the changes"

角色 role 是稳定职责；任务 task 是当前安排；状态 status 是运行活动；工具 current_tool 是执行程序。Backend 运行 pytest 依旧是 Backend，只是状态变为 TESTING。

Wrapper 注册 Agent 并跟踪进程生命周期；进程/工具观察提供基础活动信息。真实 Codex daemon 的工具可能不在 TUI 子进程树内，基础模式不保证能观察每次编辑、测试、用户输入等待或原生子 Agent。

可包装已安装的其他可执行程序，例如 uv run office-run claude --id reviewer-1 --name Reviewer --role reviewer --repo /path/to/your-repo。其他 Provider 使用 wrapper/进程回退；当前原生结构化集成只支持 Codex。

出现空办公室：先确认已启动真实 wrapper，再检查 Project 筛选是否与 Agent 的 repository/worktree 匹配。定义一个 Tester 本身不会创建角色。

4 · 稳定角色与项目配置

编辑你选用的办公室 YAML。定义必须属于实际工作仓库；如果 project.path 仍指向 Agent Office，自然不会匹配另一个工作仓库的定义。

project:
  name: my-project
  path: /path/to/your-repo
agents:
  - id: tester
    name: Tester
    role: tester
    responsibilities:
      - Run unit tests
      - Investigate failures
server:
  host: 127.0.0.1
  port: 8000
native:
  codex:
    enabled: false

例如保存到 config/local-office.yaml，重启服务：

AGENT_OFFICE_CONFIG=config/local-office.yaml uv run agent-office
uv run office-run codex --id tester-1 --definition tester   --parent lead --repo /path/to/your-repo

服务根据 repository/worktree 范围匹配 definition。项目默认名称、角色和职责优先于 wrapper 默认身份；真实非生成型原生语义可进一步补充。生成的原生 nickname 和 null role 不会覆盖项目 Tester 的稳定语义。

未指定 --id 的定义型启动会生成独立实例 ID；普通同名启动则可能复用由名字派生的 ID，建议日常显式指定。配置在服务启动时加载，修改定义后需重启服务。

多项目可在 projects 中分别配置 name、path、agents。相对项目路径按配置文件上级目录解析，采用 config/*.yaml 时通常就是仓库根目录；绝对路径更直观。示例见仓库 config/semantic-agents.example.yaml。

服务没有身份认证，预期只监听 127.0.0.1。配置示例中不要填入或提交凭据、令牌、环境变量转储。现有私有配置不需要加入 Git。

5 · Codex 原生接入：可选，但事实更完整

在本地配置中开启 native.codex.enabled: true，然后重启 Agent Office。开启开关不等于绑定线程，也不会自动创建或启动 Codex daemon。

native:
  codex:
    enabled: true
    codex_binary: codex
    reconnect_seconds: 2
    terminal_seconds: 3

已有明确 UUID：启动时自动握手

uv run office-run codex --id lead --name Lead --role lead   --repo /path/to/your-repo resume KNOWN_UUID

uv run agent-office native status

resume KNOWN_UUID 是明确身份，wrapper 注册后会在后台尝试绑定，无需手工构造 HTTP 请求。线程需要已经加载且可恢复，工作目录也必须匹配。

完全新开的会话：目前需要明确手动绑定

uv run office-run codex --id lead --name Lead --repo /path/to/your-repo

# 只有你已经确认这个 UUID 确实属于该会话时，才在另一个终端执行
uv run agent-office native bind lead EXACT_UUID
uv run agent-office native status
已确认的上游 / 当前运行时限制：Agent Office 不能从一次 fresh Codex/DevRouter 启动自动可靠取得其线程 UUID。本项目没有可靠的新会话 UUID 发现命令。不要根据最新线程、唯一线程、仓库、标题、时序或 PID 猜测；无法确认归属就保持 unbound，用现有回退继续使用。

原生子 Agent 的稳定角色

uv run office-run codex --id lead --name Lead --repo /path/to/your-repo   --native-child-definition tester resume KNOWN_UUID

# 已启动的 Agent 也可在 bind 时显式指定
uv run agent-office native bind lead EXACT_UUID --child-definition tester

前提是同一项目已定义 tester。此设置为该绑定的子 Agent 显式选择 Tester 定义，并由后代继承；它不是按任务自动区分 Tester/Reviewer 的分类器。省略时子 Agent 使用正常的原生 fallback 身份。

健康检查与恢复

uv run agent-office native status
uv run agent-office native reconnect lead
uv run agent-office native validate --thread EXACT_UUID

# 服务不是 8000 时，--server 放在子命令之前
uv run agent-office native --server http://127.0.0.1:8001 status

status 查看启用、版本、绑定、connected/degraded/unsupported 和 fallback；validate 是只读能力检查，unknown version 不会因验证而自动加入支持列表。当前精确审阅的 daemon 版本为 0.159.3、0.160.0、0.160.1、0.161.0，不是“所有更高版本”。CLI 与 daemon 版本可能不同。

重连保留当前服务会话的绑定；重启 Agent Office 后需重新绑定。原生断线释放无法确认的活动证据并退回有效基础观察，不代表 Agent 已死亡。终端 DONE/ERROR 不因观察中断而被随意清除。

观察器不会回答用户问题、批准操作、启动/中断 turn、修改 TUI 配置或重启共享 daemon。需要回答的问题仍在原来的 Codex/DevRouter 终端处理。

6 · DevRouter 使用方式

先确保 office-run 在 DevRouter 的 PATH 上。若仅通过 uv 使用项目，可以在需要集成的环境安装可编辑工具：

# 在 Agent Office 根目录执行；安装后确认当前终端能找到 office-run
uv tool install --editable .
command -v office-run

# 切到工作仓库后直接启动 DevRouter
cd /path/to/your-repo
devrouter --office

# 已知会话的明确 resume 路径
# 原生观察需要已启用且线程满足绑定要求
devrouter --office -- resume KNOWN_UUID

若工具目录未在 PATH，先运行 uv tool update-shell 并按提示重新打开终端。示例不会修改 DevRouter 的实现。不要执行 office-run devrouter；DevRouter 包装的是内部 Codex 进程。

DevRouter 的 fresh 启动同样不支持自动 UUID 相关绑定。有明确线程后，用 native status 中列出的实际 Office ID 执行 native bind，而不是假定它叫 lead。

同仓库多独立 DevRouter 会话：当前安装的 DevRouter 可能复用仓库派生的 Office ID，不能安全把两条 native thread 绑定到同一 ID。并行使用独立会话时，建议用 office-run --id lead-a、--id lead-b 启动 Codex；原生确认的子 Agent 仍有各自身份。这个外部限制尚未修复。

7 · 选择、导航与键盘

扫视→选中 Agent→看明确关系→读详情→Escape 回全局
操作结果
点击角色 / Team 按钮脚下圈和名字底板强调选中 Agent；详情同步更新。
悬停角色快速看完整语义名称、角色和状态，不打开完整卡片；不展示问题、提示词或原始命令。
详情里的 Parent / Children / Waiting on跳转当前项目中可见的直接关系目标；不存在或被过滤的目标显示 Not in this view。
Escape / 关闭详情 / 点击空白办公室清除焦点，恢复全局强调；不改变 Agent 状态、位置或 cue。
Tab → Enter 或 Space按 DOM 顺序访问并选择 Team 按钮；键盘焦点有可见边框，选中状态可被辅助技术读取。
Project筛选项目；不可见的关系不会生成跨项目幽灵连线。

选中时只有明确的父/直接子、当前等待目标、反向等待者和有效交互端点得到上下文强调。无关角色略微变淡，仍可见。用户输入等待和 ERROR 不因选中别人而消失。

拥挤时标签按用户注意 → 选中 → ERROR → 悬停 → 等待关系端点 → 普通角色排序。普通标签可能隐藏，可通过 Team 按钮查看完整名字；焦点不让角色重新换座位。

系统开启 减少动画 / prefers-reduced-motion 后，身体摆动、脉冲和移动交互包减弱或变为静态符号，角色换区仍保留较短路径移动。应用内暂时没有单独偏好开关。

窗口宽度 ≥1200px 时详情在右侧，较窄时在办公室下方，需要向下滚动。办公室保持完整比例缩放，没有缩放/平移控制。Codex 用量与昼夜景色只是额度环境提示，不是 Agent 当前活动证据。

符号含义与持续时间
? / NEEDS YOU当前明确等待用户输入，持续到该事实解除。
↔ / Child wait当前明确等待对象；等待解除即移除连线。
→新子 Agent 开始后的短暂委派提示，约 3 秒。
✓子 Agent 新进入 DONE 后的完成/交接提示，约 3 秒。
!ERROR 的持续标记，刚进入时有约 4 秒短暂强调；不表示父 Agent 也失败。

普通父子关系不会画永久组织树。重连快照也不会重播历史委派或交接；错过短暂 cue 是预期的，目前没有时间线或历史回放。

9 · 日常使用流程

  1. 开始：启动服务，打开真实模式，检查 connected 和正确 Project。
  2. 启动工作：给独立 wrapper 分配唯一 Office ID；原生已知 UUID 则用明确 resume/绑定。
  3. 扫视：先找 NEEDS YOU 和 !，再看工作区和短暂协作符号。
  4. 检查：选中 Agent，阅读 Role / Responsibilities / Current Task / Current State / Current Tool 和直接关系。
  5. 处理：需要回答、批准或修改任务时回原 Agent 终端操作；办公室是观察与导航界面。
  6. 收尾：确认完成/离场，记下遇到的问题。工作流先保持正常使用，不为了“让动画出现”人为注入状态。

服务状态主要在内存中，不是历史档案。刷新 UI 不等于停止 Agent；关闭观察页面不等于终止任务。服务重启会丢失当前 native 绑定，需要重新建立明确绑定。

10 · 常见问题

页面 disconnected / reconnecting

检查服务终端和地址，执行 curl http://127.0.0.1:8000/health。调整端口后同时调整 wrapper/native CLI 和网页地址。native 观察健康与网页 WebSocket 连接是两回事。

办公室没有 Agent，或者只有模拟角色

确认正在真实模式首页，使用 wrapper 启动 Agent，检查 Project 筛选及 repository/worktree。定义 YAML 不会自动启动 Agent；后启动服务也可能错过 wrapper 开始事件，进程发现只能提供回退，不保证还原完整原生关系。

Agent 显示 THINKING / IDLE，但实际正在编辑或跑测试

先看 agent-office native status 是否 enabled、bound、connected。fresh 未绑定、unknown version 或工具在 daemon 外部托管时，基础进程观察可能缺失活动。IDLE 可能是超时回退；单纯提高 idle_timeout 不会补齐原生事实，目前也没有文件系统 CODING watcher。

native bind 失败 / unsupported / degraded

核对 Office ID、精确线程 UUID、线程已加载、匹配仓库和配置启用状态。用 status 查看失败类别；有明确 UUID 时运行 validate。unsupported 不要绕过版本门禁；记录版本与诊断后继续回退。不要重启共享 daemon 或用 newest/only thread 猜绑定。

没有自动出现 Tester 子 Agent，或名称是原生 nickname

自动原生子 Agent 需要父线程明确绑定和原生父子证据。项目 tester 定义还需通过 native-child-definition/child-definition 显式分配；没有定义时使用 fallback nickname 是正常行为。定义存在不代表系统会按任务推断角色。

问了我一个问题，但没有 NEEDS YOU

原生结构化 requestUserInput 是已确认信号；普通聊天提问、审批等待未被统一识别。办公室不解析自然语言推断等待。记录原终端发生了什么、是否绑定、是否有明确结构化等待；不要把所有提问都当成同一种原生事实。

同仓库两个 DevRouter 会话合成一个角色

当前 DevRouter 可能复用仓库派生的 Office ID，这是已知外部限制。并行时用不同 office-run --id 启动 Codex，避免将两条线程绑定到同一身份；不要按仓库自动猜测。

连线、名字或角色在拥挤区域看不清

先通过 Team 按钮选中相关 Agent，再沿详情关系查看；NEEDS YOU、选中和 ERROR 标签优先。极端密度仍可能有标签/连接线重叠，请记录人数、视窗尺寸和截图；目前没有缩放平移或组织图。

点击角色没有反应 / 详情看起来消失

可用 Team 按钮确认选择，检查 Project 筛选。窄于 1200px 时详情在下方，向下滚动。若升级后仍是旧 UI，重新 npm run build 并刷新浏览器。

Codex 用量 unavailable

当前本机会话可能没有可读额度样本；不影响普通 Agent 显示。额度与 Agent 活动是独立来源，不要用 daylight/额度来判断任务是否在运行。不要为排查导出凭据、完整配置或私有会话内容。

刷新后没有刚才的委派/交接动画

刷新收到的是当前快照，不重播旧 cue；这属于设计行为，不是委派关系丢失。只有当前明确等待关系才持续画线。

11 · 记录使用反馈，之后再决定开发

先积累真实工作中的问题，无需一次性测试所有状态。每个问题记一条，区分运行事实不准确、身份/关系问题、显示/布局问题、接入摩擦或已知限制。最有价值的是预期与实际差异、最短复现、影响和证据。

第一次使用可以留意这些问题

  • 能否很快发现需要你和失败的 Agent？选中后是不是更好理解？
  • Lead / Tester 的等待和交接是否符合实际？有没有把普通父子关系误看成等待？
  • 拥挤区域、笔记本窗口和下方面板是否影响使用？键盘和减少动画是否舒服？
  • 真实状态与终端行为差在哪里？是 native 未绑定/unsupported，还是已有信号显示有误？
  • 启动、明确绑定和 DevRouter 的步骤哪里最费力？已有约束是否阻碍工作？

使用后把记录发回来，可以按“阻塞工作 → 事实错误 → 交互/可读性 → 视觉改进”排序，再选择下一批开发范围。本次只更新使用文档，不开始 Phase 4D。
